# llama-server: host Metal and Jetson CUDA

Phase 5 (D27/D28) moves the deployment seam to HTTP: the resolver node talks to a `llama-server`
process over HTTP instead of linking llama.cpp into the process. `backend: inprocess`
(llama-cpp-python) stays the default for host unit tests and ordinary development; `backend:
http` is what batch benchmark runs and hardware use. Both send the identical GBNF grammar
string, generated by the same `grammar.py`, as the `grammar` field of the request.

## Building llama-server

The pinned source is `third_party/llama.cpp` (tag `b10941`, commit `4a89937`, see CLAUDE.md).
It is not built into the Docker image; the container has no CUDA/Metal, and the whole point of
the HTTP seam is that llama-server runs on the host.

```bash
cd third_party/llama.cpp
cmake -B build -DGGML_METAL=ON -DLLAMA_CURL=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build build --target llama-server --config Release -j$(sysctl -n hw.ncpu)
```

Binary lands at `third_party/llama.cpp/build/bin/llama-server`. `-DLLAMA_CURL=OFF` avoids a
libcurl dependency that is only needed for the server's own model-download feature, unused
here since models are already local under `models/`.

## Running it on the macOS host (Metal)

```bash
./third_party/llama.cpp/build/bin/llama-server \
  --model models/phi3-mini-4k-instruct.Q4_K_M.gguf \
  --port 8080 \
  --ctx-size 2048 \
  -ngl 99
```

`-ngl 99` offloads every layer to Metal (Phi-3 mini has far fewer than 99, so this is just
"all of them", same convention as llama-cpp-python's `n_gpu_layers=-1`). `/health` returns
`{"status": "ok"}` once the model is loaded.

Point the resolver at it from inside the container with the default parameters
(`backend:=http`, `backend_url:=http://host.docker.internal:8080`), or directly from a host
Python process with `ResolverCore(backend="http", backend_url="http://127.0.0.1:8080", ...)`.

## Verifying the container's route to the host

`host.docker.internal` is Docker Desktop's documented host alias; it is not assumed, it was
checked from inside the running container as part of this phase:

```bash
docker compose -f docker/docker-compose.yml exec dev bash -lc \
  "getent hosts host.docker.internal; curl -s -o /dev/null -w '%{http_code}\n' http://host.docker.internal:8080/health"
```

Observed: `host.docker.internal` resolves to the Docker Desktop gateway address and the health
check returns `200`. No extra `extra_hosts` entry or compose change was needed; Docker Desktop
on macOS wires this up by default. A Linux host without Docker Desktop would need an explicit
`extra_hosts: ["host.docker.internal:host-gateway"]` in `docker-compose.yml`, which is not
required here and is left as a note for a future non-macOS development host rather than
applied speculatively.

## Jetson CUDA (flags only, build lands in Phase 9)

On the Orin NX, `llama-server` is the same binary target, built with CUDA instead of Metal:

```bash
cmake -B build -DGGML_CUDA=ON -DLLAMA_CURL=OFF -DCMAKE_BUILD_TYPE=Release
cmake --build build --target llama-server --config Release -j$(nproc)
```

Run identically, minus `-ngl` tuned to the Orin NX's VRAM (Phase 9 measures and records the
actual value; `-ngl 99` is a safe starting point for a model this small). On hardware the
resolver runs on the Jetson itself, so `backend_url` becomes `http://127.0.0.1:8080`: same
code path, same request shape, only the URL changes (S2 in `docs/archive/superseded-decisions.md`).
This file documents the flags only; Phase 9 is what actually builds and measures this on the
Jetson, since v2's hardware plan explicitly avoids compiling llama-cpp-python from source
against JetPack's CUDA (see superseded-decisions.md S2 point 1).
