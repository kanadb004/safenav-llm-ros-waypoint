# What simulation cannot de-risk

Written in Phase 9 (PLAN.md section 15) as an honest list of what no amount of further
simulation work can answer, so Phase 10 budgets time and expectation for it rather than being
surprised. Each item names why simulation specifically cannot reach it, not just that it is
untested.

## 1. Real sensor noise feeding AMCL

The loopback simulator (`safenav_sim/loopback_sim_node.py`, D30, used because Gazebo does not
run in this project's container) has noise-free odometry and no real LIDAR returns; `amcl`'s
noise parameters in `nav2_params.yaml` were loosened specifically to match that noise-free
input (see the comment at the top of `nav2_params_hardware.yaml`). A real Create 3's wheel
odometry drift and a real LIDAR's beam noise, multipath and dynamic obstacles cannot be
produced by a loopback simulator by construction; AMCL's particle filter behavior against real
noise (localization jitter, recovery from kidnapped-robot style TF jumps, convergence time) has
never been exercised in this project and will not be until the robot localizes on a real map.

## 2. Create 3 docking behaviour

Nothing in this project implements or tests docking (returning to a charging dock and engaging
the physical connector). `room_annotations.json` has a `charging_dock` room as a named waypoint,
but reaching that waypoint's pose is ordinary navigation, not docking; the Create 3's own
docking action (vision or IR-based dock detection, final approach control) is iRobot firmware
and companion-computer behavior this project has never invoked, in simulation or otherwise.

## 3. Thermal throttling of the Orin under sustained inference

The Orin NX's CPU/GPU frequency governor throttles under sustained thermal load; this project's
only latency measurements are from a macOS laptop with its own (different) thermal behavior,
already flagged once as a confound (D44: a sustained macOS session measured 6478/7220/7768 ms
versus 3026/3497/9448 ms cold, `docs/results/RESULTS.md` section 3). The Orin NX has a smaller
thermal mass and a different cooling solution (fan or passive, depending on carrier board) than
a laptop; nothing about its thermal response under a long trial suite can be inferred from the
macOS numbers. Phase 10 should run a sustained-session latency check analogous to the Phase 5
one specifically to catch this, and should not assume a cold-start measurement generalizes to
an hour-long trial suite.

## 4. Real human phrasing versus persona-generated phrasing

Every command in every benchmark and trial suite in this project (`synthetic_500.jsonl`,
`e2e150`, the calibration sessions) was generated by an LLM persona pipeline (D7, recorded
deviation), not spoken or typed by a real person. Resolver accuracy, the calibrator's
separability, and every reported false-pass/false-abstain rate are all measured against
machine-generated phrasing. Real phrasing brings disfluency, self-correction mid-command,
regional phrasing, and background noise through the hardware microphone path, none of which a
text-based simulation pipeline can produce no matter how it is varied. This is the single
largest generalization gap in the project's accuracy numbers and cannot be closed without
collecting real commands from real speakers.

## 5. Audio hardware for TTS

`/tts_text` is published and subscribed to in the Phase 6 launch test
(`test_semantic_nav_launch.py`), and `espeak-ng` is installed in both Docker images, but no
audio has ever actually played through a speaker in this project. Whether the robot's audio
output device is configured correctly, whether `espeak-ng`'s voice is audible and intelligible
at a reasonable volume in a real room, and whether its latency (process spawn plus synthesis
time) is acceptable for a clarification prompt the user is meant to respond to, are all unknown
until real audio hardware is in the loop.

## 6. The hardware latency gate itself

Listed here as well as in `bringup-checklist.md` item 9 because it is the risk most likely to
block everything else: the Orin NX's "about 0.7 s" latency is the specification's expectation,
never measured on any hardware in this project (PLAN.md section 13, 15.0). The only real
measurements are from a 5 to 10 times faster-than-container macOS Metal host and are themselves
above the 3000 ms gate (p50 3797 to 3942 ms, p90 5160 to 5540 ms). Simulation cannot produce an
Orin NX measurement; only an Orin NX can. If the real number lands closer to the macOS figures
than to 0.7 s, the hardware profile's `timeout_ms: 3000` will route most commands into
clarification, and the project's threshold and timeout values will need to be revisited with a
recorded deviation before any accuracy trial is meaningful.
